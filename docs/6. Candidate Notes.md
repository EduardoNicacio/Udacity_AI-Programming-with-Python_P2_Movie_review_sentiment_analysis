## 1. Elevator Pitch

**The Problem:** CineScope's recommendation engine needs to understand whether a user review is positive or negative — but the raw task is harder than it looks. The IMDB dataset ships as a ~85 MB gzipped tar archive containing roughly 100,000 individual `.txt` files across four labeled directories. The starter notebook had **18 stub sites across 10 code cells** — covering everything from the file reader and PyTorch `Dataset` interface to the transformer's classification head, mean-pooling step, accuracy function body, and the entire training loop inner block — plus a conclusion markdown cell. More subtly, the notebook shipped with the last two lines of `calculate_accuracy()` already written (`accuracy = (total_correct / total_samples) * 100` / `return accuracy`) while the variables those lines reference — `total_correct` and `total_samples` — were absent, meaning a naive fill that just added code to the end of the function would have produced a `NameError` at inference time.

**The Solution:** A complete, template-faithful fill of `SentimentScope_starter.ipynb`: all stubs replaced with production-quality code, all assert cells passing silently, and two architectural additions grafted into `DemoGPT` without touching any pre-written layer. The file reader uses `os.listdir()` with a `.txt` guard and UTF-8 encoding; `IMDBDataset.__getitem__()` calls the tokenizer with `padding='max_length'` and `.squeeze(0)` to deliver a 1-D `(128,)` tensor while returning the label as a raw numpy int64 (satisfying the `isinstance(label, (int, np.integer))` assert). `DemoGPT` gains one `nn.Linear(128, 2, bias=False)` classification head in `__init__` and two lines in `forward`: `torch.mean(x, dim=1)` for mean pooling followed by the head call. `calculate_accuracy()` gets the full evaluation body inserted *before* the existing final two lines. The training loop fills five sequential operations: forward pass, cross-entropy loss, `optimizer.zero_grad()`, `loss.backward()`, `optimizer.step()`. `EPOCHS` is raised from 3 to 5 — explicitly invited by the notebook's own "Try training for more than 3 epochs!" note — to reliably clear the 75% accuracy threshold. A model checkpoint cell and a substantive conclusion markdown are added after the test evaluation cell.

**The Result:** Training converges cleanly across all 5 epochs on CUDA, with cross-entropy loss falling from **0.6906 → 0.3136** and validation accuracy climbing from a random-weight baseline of **51.92%** to a peak of **79.48%** at epoch 4. Final test accuracy on all 25,000 IMDB test reviews: **76.85%** — 1.85 points above the 75% pass threshold. All 10 assert cells produce no output. The deliverable notebook executes 40 numbered cells with 0 error outputs, 4 embedded visualizations, and both required artifacts present: `SentimentScope_starter_1.ipynb` and `sentimentscope_checkpoint.pth`. A rubric audit against `5. Rubric_1.md` scores **8/8 criteria — 100% PASS**.

### Key Design Decisions

| Decision | Rationale |
| :--- | :--- |
| **`squeeze(0)` in `__getitem__`** | The tokenizer called with `return_tensors='pt'` returns `input_ids` of shape `(1, 128)` — a batched single item. The assert `input_ids.shape[0] == train_dataset.max_length` fails unless the leading dimension is removed; `.squeeze(0)` collapses it to `(128,)` before returning |
| **Return label as numpy int64, not a tensor** | `self.data.iloc[idx]['label']` returns numpy int64, which passes `isinstance(label, (int, np.integer))` directly. Converting to `torch.tensor()` inside `__getitem__` would make it a zero-dimensional tensor and fail that assert. The DataLoader's default collate converts it to a LongTensor correctly at batch time |
| **Insert `calculate_accuracy()` body before the existing two lines** | The stub cell already contained `accuracy = (total_correct / total_samples) * 100` and `return accuracy`. Any approach that appended code after those lines would have placed the return statement in the middle of the function body. The body must be inserted *before* the existing content |
| **`EPOCHS = 5`, not 3** | With d_embed=128, 4 blocks, and AdamW at 3e-4, epoch 3 yields val acc 77.16% and epoch 2 first clears 75% — but the test score at epoch 3 could easily fall below 75% on a different seed or GPU. The notebook itself says "Try training for more than 3 epochs!" — `EPOCHS = 5` is the minimal change that reliably clears the threshold (test score 76.85%) without touching the config |
| **Mean pooling over CLS token** | The notebook instructed `torch.mean(x, dim=1)`. While using the CLS token output (`x[:, 0, :]`) is the BERT convention, that would require changing the tokenizer, which is not part of this project's scope. Mean pooling across all 128 token positions is the correct interpretation of the spec |
| **`nn.Linear(d_embed, num_classes, bias=False)`** | The notebook's instruction note for the classification head explicitly stated `bias set to False (optional; bias can be excluded to slightly simplify computations)`. Following the spec exactly avoids potential shape mismatches in the downstream assert |
| **Unconventional gradient order in the training loop** | The stub comments explicitly ordered the five TODOs as: forward → loss → zero_grad → backward → step. While the canonical PyTorch idiom zeros gradients before the forward pass, both orderings are mathematically equivalent for non-accumulative training — clearing accumulated gradients before calling `.backward()` is what matters |

## 3. Pipeline Design Principles in Practice

**One function, four directories.** `load_dataset()` is a pure file reader: it takes a folder path, lists all `.txt` files, opens each with UTF-8 encoding, and returns a list of strings. It is called exactly four times — `train_pos_path`, `train_neg_path`, `test_pos_path`, `test_neg_path` — and the labels are applied by the DataFrame constructor, not inside the reader. This keeps I/O decoupled from labeling and makes the function trivially testable.

**Late tokenization, just-in-time.** The tokenizer is never called on the full 25,000-row DataFrame up front. Instead, `IMDBDataset.__getitem__()` calls it per-item. This avoids allocating a 25,000 × 128 tensor in memory during dataset initialization and lets the DataLoader naturally parallelize tokenization across workers in any environment where `num_workers > 0` is used.

**Strict tensor contract at the Dataset boundary.** The `__getitem__` contract is: return a `(torch.Tensor of shape (128,), numpy int64)` tuple. The shape `(128,)` is enforced by `.squeeze(0)`, and the numpy int64 is left unconverted. The DataLoader's default collate then stacks these into `(B, 128)` input tensors and `(B,)` LongTensors — exactly what `nn.CrossEntropyLoss` expects without any additional casting.

**Classification head as the minimal surgical addition.** The pre-written `DemoGPT` architecture is a generation-style transformer with everything in place except the two lines needed for classification: a pooling step and a classification head. Adding `self.classification_head = nn.Linear(128, 2, bias=False)` in `__init__` and two lines in `forward` is the complete delta. All other layers — embeddings, blocks, layer norm — are untouched, matching the project's design philosophy of modifying only what is necessary to adapt the architecture for the new task.

## 6. Challenges & Resolutions

### Challenge 1 — The `calculate_accuracy()` pre-written tail trap

**What happened:** The stub cell contained the function signature, the docstring, and the last two lines of the function body: `accuracy = (total_correct / total_samples) * 100` and `return accuracy`. A planner that reads "fill in the function" and appends code after the existing content would place the implementation after the `return` statement, making it unreachable dead code — and `total_correct` and `total_samples` would remain undefined, producing a `NameError` on the first call.

**Resolution:** The OpenCode prompt for this cell stated explicitly: "Add the full evaluation body BEFORE those two lines, keeping them unchanged." The resulting code inserts `model.eval()`, `total_correct = 0`, `total_samples = 0`, the `torch.no_grad()` context, the batch loop, and the `argmax` prediction step — all before the existing content, which remains as the function's final two lines.

### Challenge 2 — The `squeeze(0)` shape contract

**What happened:** The tokenizer called with `return_tensors='pt'` always returns a batched tensor. For a single input string, `encoding['input_ids']` has shape `(1, 128)`. The assert `input_ids.shape[0] == train_dataset.max_length` checks `.shape[0]` against 128 — which passes if the tensor is `(128,)` and fails with shape `(1, 128)` where `.shape[0]` is 1.

**Resolution:** `.squeeze(0)` removes the leading batch dimension, converting `(1, 128)` to `(128,)`. This is distinct from `.squeeze()` with no arguments (which would also remove any dimension of size 1, potentially corrupting sequences padded to exactly one token) and from `.reshape(128,)` (which copies). `.squeeze(0)` is the precise, safe choice.

### Challenge 3 — `EPOCHS = 3` is insufficient to reliably clear 75%

**What happened:** The epoch 1 validation accuracy of 71.12% is safely below the 75% threshold. Even epoch 2 clears it at 76.12%, but the margin is narrow — a different random seed, a slightly different GPU, or a different batch ordering could land epoch 3 below 75%. The rubric requires the test set accuracy to exceed 75%, not the validation accuracy at any single epoch.

**Resolution:** `EPOCHS = 5` with the peak at epoch 4 (79.48% val) delivers a test accuracy of 76.85% — safely above the threshold with a meaningful margin. The cost is roughly 40% more training compute, which on this architecture and dataset size is negligible.

### Challenge 4 — Mild overfitting between epoch 4 and 5

**What happened:** Validation accuracy peaks at epoch 4 (79.48%) and drops to 78.88% at epoch 5. The test accuracy (76.85%) is 2.03 points below the epoch 4 peak, suggesting the model trained at epoch 5 generalizes slightly less well than it would have if training had been stopped earlier.

**Resolution:** For the purposes of this submission, 76.85% clears the 75% bar comfortably and the project passes. To close this gap in a real production setting, the appropriate fix would be to checkpoint the model at the end of each epoch and restore the best-validation checkpoint for final testing — a straightforward addition outside this project's scope.

## 10. Retrospective

### What I'd Do Differently

1. **Checkpoint the best-epoch model, not just the final one.** The model saved to `sentimentscope_checkpoint.pth` is the epoch-5 state, which achieves 76.85% test accuracy — but the epoch-4 model peaked at 79.48% validation. Adding a best-checkpoint pattern (save when `val_accuracy > best_val_accuracy`) would have saved the stronger model and closed the 2.63-point gap between peak validation and final test score.

2. **Probe truncation loss before committing to MAX_LENGTH=128.** The review-length histogram shows that IMDB reviews are frequently much longer than 128 tokens. At 128 tokens with `[CLS]` and `[SEP]`, a review of 300 words loses roughly its second two-thirds. Understanding the accuracy penalty of this truncation — by running a quick experiment at 256 or 512 tokens on a small subsample — would have made the MAX_LENGTH decision explicit and evidence-based rather than inherited from the template default.

3. **Verify the gradient order explicitly before submission.** The training loop fills five TODOs in the order: forward → loss → zero_grad → backward → step. This is valid but unconventional (the canonical pattern zeros gradients before the forward pass). Running a one-batch sanity check that confirms loss decreases after the first update — rather than trusting the training log — would have caught any wiring error immediately rather than relying on the loss curve as the sole indicator.

4. **Run the accuracy function on a fixed tiny batch first.** Before training, calling `calculate_accuracy()` on a 2-batch slice of the training set with known labels would have verified the argmax/comparison logic independently of the full val loop. The pre-training 51.92% baseline is strong evidence it worked, but a controlled unit test would be conclusive.

### What Worked Well

1. **The section-per-stub prompt structure.** Each of the 14 stub sites (4 paths, 1 reader, 4 data loads, 4 EDA cells, 3 IMDBDataset methods, 2 DemoGPT additions, 1 accuracy body, 5 training TODOs, 1 test cell, 1 checkpoint cell, 1 conclusion) was its own named section in the OpenCode prompt, with no cross-references. The planner never needed to hold multiple contexts simultaneously, and the resulting notebook had zero misfires.

2. **Leading with the "insert before" instruction.** The `calculate_accuracy()` section flagged the pre-existing tail before describing what to add. In practice this meant the planner wrote the loop first and landed exactly where the existing `accuracy = ...` line was waiting for it.

3. **Justifying `EPOCHS=5` with the notebook's own text.** The prompt quoted "Try training your model for more than 3 epochs!" verbatim as the rationale for changing `EPOCHS`. A planner that saw a spec change without justification might have treated it as an error and reverted it; quoting the instruction anchored the decision in the project's own voice.

4. **Reading the `calculate_accuracy()` stub as a booby trap, not a starter.** The two existing lines at the bottom of the function body were the most dangerous content in the notebook — they *look* like a complete stub but reference variables that don't exist yet. Identifying this pattern before writing any code, rather than after a `NameError` at runtime, eliminated the main failure mode for this cell.

### The AI Partnership

> "This project is structurally harder than a data transformation exercise: it requires implementing the internal contracts of a PyTorch module family from scratch, wiring a multi-step training loop correctly, and doing it all in a single coherent pass over a notebook where some cells are complete, some are partial, and one is a trap. The AI's role was to hold the entire specification surface — 14 stub sites, 10 assert contracts, 5 pre-written class bodies, and an unconventional gradient order — simultaneously and fill each slot without contaminating any of the surrounding context. The human's role was to read the stubs first and notice the `calculate_accuracy()` tail before it became a runtime error, to decide on `EPOCHS=5` as the minimal safety margin, and to verify the training log as proof-of-convergence rather than proof-of-correctness. Speed comes from the AI. Judgment about what can go silently wrong comes from the human."

That division held throughout. The loss curve from 0.69 to 0.31 across 3,520 gradient steps, and the test result of 76.85%, are the machine's work. The decision that epoch-5 was good enough to submit rather than running epoch 6 — and that the 96 duplicate reviews in `train_df` were not worth cleaning for a first pass — was the human's.

### Final Thoughts

On paper, SentimentScope is a transformer tutorial: implement a file reader, wire a PyTorch Dataset, bolt a classification head onto a pre-written model, fill in a training loop. In practice, the interesting engineering is concentrated in the seams — a tokenizer that silently adds a batch dimension that must be squeezed, a function stub with pre-written code that must be preceded rather than followed, a 3-epoch default that sits 1.85 points below the pass threshold, and a gradient-zeroing order that is correct but non-canonical. The model itself never struggled: loss fell cleanly from near-random entropy (0.69) to 0.31 over five epochs, validation accuracy peaked at 79.48%, and the test set delivered **76.85%** — 1.85 points above the bar, on 25,000 reviews it had never seen, from a 4-block transformer trained from scratch. The architecture earned its pass.
